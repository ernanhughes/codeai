# Pre-registration: W2-2, the acceptance basis

**Registered:** 2026-09-18, before any implementation choice.
**Subject:** CodeAI `c1d4418` (main, after W2-1).

## The question is not the obvious one

The obvious question — *can `AcceptanceRequest` carry an `action_id`?* — is trivial and wrong. The
real one:

> When an acceptance claims that an effectful action is part of the basis for completing a task, can
> the runtime establish that the accepted state is actually downstream of that action?

And its corollary, which decides the shape of the answer:

> A task may legitimately accept an artifact without caring how it was produced.

An artifact can be imported, written by hand, generated by a model, or already correct. Forcing a
fictional action into that history to satisfy a schema would be worse than the gap it closes.

## The distinction this seam rests on

```text
accepting a result  ≠  accepting an action as the producer of that result
```

So the basis is modelled explicitly, not mandated:

```text
acceptance basis
  |- artifact / check basis     "I accept this verified result"
  `- effect / action basis      "I accept this verified result as the outcome of action A"
```

Two invariants:

1. If an acceptance **claims** an action as part of its basis, that action-to-accepted-state
   relationship is enforced, not caller-asserted.
2. If an acceptance **does not** rely on an action, the record must not imply that it does.

## Step 1: measure before implementing

Case A is a falsifier, and it runs first. If a second process can already derive the action
unambiguously from the durable record, this relationship is **DERIVED** and no seam is needed —
that result gets recorded and the work stops there.

```text
A   action A changes state to H1
    check runs against H1 and PASSes
    acceptance names artifact and checks, and no action
    -> can another process derive A unambiguously?
```

The probe tests derivation under adversarial conditions, not just the happy one: a second action
that observes the same state, an action belonging to another task, a replay, and a check with no
state binding at all.

## Step 2, only if A shows a real gap: the hostile cases

| Case | Setup | Expected |
|---|---|---|
| B | A → H1, B → H2, check PASSes H2, acceptance claims A | effect-basis refused |
| C | B → H2, check PASSes H2, acceptance claims B | allowed |
| D | action belongs to task X, acceptance to task Y | refused |
| E | action FAILED or DENIED, a later check passes | may not be claimed as producer; the task may still be acceptable on artifact/check basis |
| F | action effect UNKNOWN or REPORTED | may not be claimed as producer; artifact/check acceptance still available |
| G | cognition-only task, no action at all | ordinary acceptance unaffected |
| H | A observed H1, check PASSed H1, world moved to H2 | accepting H2 cannot borrow A's chain |

The enforced chain for an effect-based acceptance, using the existing state-binding machinery rather
than a new identity system:

```text
action.completed
      -> runtime-observed state H
      -> a check bound to H
      -> PASS
      -> acceptance naming that action and that check
```

with the runtime checking: same task, the action exists, its effect state is `OBSERVED`, the check
examined that same observed state, the check passed, and the acceptance cites it.

## What this would establish, and what it would not

```text
action -> accepted-state binding        what it is
causal proof that A produced H          what it is not
```

The before/after readings are proximity, not a transaction (Chapter 19's limit, unchanged). What the
record would support is: *action A was followed by runtime observation H, and the accepted
verification examined H.* Nothing stronger, and the naming should say so.

## Registered predictions

1. Case A will be derivable in the simple shape and ambiguous in at least one adversarial shape,
   which is what makes it a gap rather than a nuisance.
2. The most likely ambiguity is two actions observing the same state hash — a no-op action, or a
   denial that recorded the pre-effect state, colliding with the real one.
3. `UNKNOWN`/`REPORTED` (W1-R1) will do most of the refusing work in case F, without new machinery.
